# Database project

Колоночная БД на Kotlin. Внешних зависимостей нет, нужен только JDK 21 (Gradle подтянется через wrapper).

## Запуск

```bash
./gradlew run
./gradlew run --args="/tmp/demo"
```

Данные сохраняются в `./data` (или в каталоге из `--args`) и переживают перезапуск: повторный запуск читает таблицу, созданную раньше. Чтобы начать с чистого состояния, удалите каталог.

## Как хранятся данные

- Колонка лежит в файле `<таблица>/<колонка>.col` как последовательность блоков по 8192 значения; каждый блок сжат Deflate. Блоки только дописываются в конец файла, записанное не переписывается.
- Свежие строки лежат в памяти и в журнале `wal.log` (строка целиком, с контрольной суммой). Когда набирается целый блок, он дописывается в файлы колонок, а журнал сокращается до остатка. Поэтому `flush` стоит столько, сколько новых данных, а не сколько всего в таблице.
- Кэш хранит только неизменяемые блоки, уже записанные на диск, в пределах бюджета (по умолчанию 256 МБ, у `load` параметр `cache=` в МБ). Таблица может быть много больше кэша: в памяти остаются недавно читавшиеся блоки, остальные подгружаются с диска по требованию.
- После сбоя при открытии таблицы лишние блоки (запись оборвалась на части колонок) отбрасываются, дозаписанный не до конца хвост журнала отсекается, строки из журнала, которые уже есть в блоках, пропускаются.
- Данные в старом формате (`COL1`, колонка целиком в одном блоке) не читаются: удалите каталог данных и загрузите заново.

## Консоль

```bash
./shell.sh
./shell.sh /tmp/demo
```

Стрелки вверх/вниз листают историю команд, влево/вправо двигают курсор, Ctrl-D выходит. Запускать нужно через `shell.sh`, а не через `gradlew`: Gradle подменяет ввод, и стрелки не работают. Нужен терминал с `stty` (macOS, Linux); без него ввод работает без стрелок.

Команды: `help`, `tables`, `create table`, `describe`, `drop table`, `insert`, `get`, `select ... where ... order by` (печатает первые 50 строк и общее число), `count/sum/avg/min/max`, `stats` (размер файлов, сжатие, журнал), `flush`, `load`, `dashboard`, `exit`. После каждой вставки данные сразу пишутся на диск.

Вместе с консолью поднимается дашборд http://localhost:8765 (другой порт: `./shell.sh port=9000`, без дашборда: `./shell.sh --no-dashboard`, бюджет кэша блоков в МБ: `./shell.sh cache=32`). Он показывает все таблицы каталога данных с размерами файлов и сжатием (у таблиц, которые в этой сессии ещё не открывали, число строк не показывается), а каждая команда из консоли сразу попадает на графики.

Сценарий «консоль, дашборд, нагрузка на настоящих данных» в одной сессии:

```
db> tables                        # что лежит в базе
db> insert users id=3 name=Egor   # операция видна на дашборде
db> load from=hits seconds=60     # нагрузка в фоне на копию hits, консоль свободна
db> select load_hits where c7 > 1000000
db> load stop                     # остановить раньше срока
```

`load` принимает те же параметры, что и `./gradlew load` (`load help`). Таблицу `hits` предварительно загружают через `importcsv`. Нагрузка идёт на копию `load_hits`, исходная таблица не меняется.

Удаления и изменения записей нет: интерфейс `Table` их не предусматривает.

## Загрузка своих данных (CSV/TSV)

```bash
./gradlew importcsv --args="файл.csv"
./gradlew importcsv --args="файл.tsv.gz table=movies limit=1000000"
./gradlew importcsv --args="help"
```

Типы колонок определяются по первым строкам (целое, дробное, boolean, иначе строка), `.gz` читается без распаковки. Данные попадают в `./data`, дальше их можно смотреть через `shell`, `inspect` и `stats`. Импорт печатает скорость, размер на диске, степень сжатия по колонкам и скорость чтения обратно.

Пример на датасете hits из ClickHouse (133 колонки без заголовка, 8,9 млн строк):

```bash
./gradlew importcsv --args="/Users/k.bushmelev/Projects/archivator/hits_v1.tsv table=hits header=false escapes=true limit=500000 columns=1-3,5-8,10,11,13,15-17"
```

Объём загрузки памятью не ограничен (блоки уходят на диск по мере заполнения), `limit` и `columns` нужны, чтобы не ждать загрузки всего файла.

## Нагрузочный тест

```bash
./gradlew benchmark                      # 100000 строк
./gradlew benchmark --args="500000"      # свой объём
./gradlew benchmark --args="100000 /tmp/bench"   # другой каталог данных
```

Замеряет скорость записи и чтения, задержки (p50/p99/max), запросы, влияние кэша и эффективность хранения (размер на диске, степень сжатия, сравнение с CSV). Данные случайные с фиксированным зерном.

## Нагрузка с живым дашбордом

```bash
./gradlew load -q
```

Открыть http://localhost:8765. Параллельно работают писатели, читатели, запросы (filter, sort, aggregate) и периодический flush; страница показывает пропускную способность, задержки, кэш, рост таблицы, размер на диске, сжатие по колонкам и память. Параметры:

```bash
./gradlew load -q --args="seconds=120 writers=2 writeRate=10000 readers=8 readRate=0 port=9000"
./gradlew load -q --args="help"
./gradlew load -q --args="dir=/tmp/load"   # другой каталог данных
```

`benchmark` и `load` пишут в `./data` (тот же каталог, что у демо и консоли) и оставляют данные после теста: смотреть через `./gradlew inspect`. Тесты владеют своими таблицами `bench_events` и `load_events`: при старте пересоздают их, остальные таблицы не трогают. Не запускайте их одновременно с консолью на том же каталоге: блокировок между процессами нет (и порт дашборда у них один). Если нужны и консоль, и нагрузка, запускайте нагрузку командой `load` из консоли.

Нагрузка на настоящие данные (таблицу можно загрузить через `importcsv`):

```bash
./gradlew load -q --args="from=hits"
```

Таблица копируется в `load_hits` (исходная не меняется), писатели вставляют копии случайных её строк, запросы (filter, sort, avg по группам) подбираются по схеме. На диске нужно место под копию таблицы.

Дашборд слушает только localhost и отдаёт одни метрики. После конца нагрузки он остаётся открытым ещё 30 секунд (`linger`).
